# OpenMuse configuration control plane

This is a runnable reference service for the shared v1 deployment and snapshot contracts. Node 24 provides SQLite transactions and Ed25519 signing; the admin uses relative, same-origin APIs. It is a single-writer local/reference implementation. The production topology in the architecture document still needs managed identity, an external signer, replicated storage, CDN deployment, monitoring and operational ownership.

## Run locally

```sh
cd services/config-control
npm ci --ignore-scripts
npm run dev
```

Read the address printed by the server. `dev-settings.json` configures its loopback address, public distribution origin, source deployment and local scope. The development entry binds to IPv4 loopback only. It creates an owner-readable key, SQLite database and public `deployment.local.json` under ignored `.local/`. It never modifies a production deployment profile or sends requests to its service endpoints.

The local admin exposes separate editor, approver, publisher and administrator identities. These are development identities, not an SSO implementation. The configured example HTTPS distribution origin is deliberately separate from loopback HTTP; to connect an actual client, place this service behind a trusted HTTPS proxy at your chosen origin and compile the resulting public deployment bundle into a development client. Production URL/certificate verification is not weakened for local testing.

## Workflow

1. Provision a scope with an installed deployment bundle through `POST /v1/admin/scopes`. Its bootstrap must already trust the configured public key and distribution/resource origins. Scope identity and trust policy are immutable.
2. Obtain `GET /v1/admin/scopes/{scope}/template`. New drafts inherit the current published snapshot and its language resources, rather than accidentally resetting to the original installation baseline.
3. Create/edit a draft containing `{snapshot, packs, note}`. Release sequence/time/resource URLs are generated by the publisher. JSON Schema and cross-field validation reject unsafe paths, out-of-policy endpoints, unsupported locales and changed message argument contracts.
4. Submit using the current draft version. Submission freezes content and records the active pointer revision. A contributor cannot approve their own change. Approval binds to the content digest.
5. Publish with that digest and expected pointer revision. If another release or rollout changed the pointer after submission, create a fresh draft and obtain a new review. Signatures, immutable resource bytes, release rows, active pointer and audit entries commit in one SQLite transaction. Repeating a completed publish is idempotent.
6. The first release serves all cohorts. Subsequent releases begin at 1%; promote to 5%, 25%, 100%, or stop at 0%. Clients without cohort routing stay on the stable release until 100%.
7. A rollback creates a new draft from old release content. Review and publish it at a **higher sequence**. Stopping rollout serves the previous version to new/older clients; clients that have already accepted a higher sequence retain it and require a higher-sequence rollback to revert content.

The admin includes snapshot and message diffs, language namespace editing, approval state, release history, cohort distribution preview and transactional audit history. The preview decodes distribution data for inspection; it does not substitute for the client's signature and compatibility checks.

## API surfaces

| Surface | Purpose |
| --- | --- |
| `GET /v1/admin/session` | Current identity, public signer metadata, development-mode indication |
| `GET/POST /v1/admin/scopes` | Authorized scopes / immutable deployment provisioning |
| `GET /v1/admin/catalog` | Installed locale and message registry |
| `GET /v1/admin/scopes/{id}` | Deployment and active-pointer revision |
| `GET /v1/admin/scopes/{id}/{template,drafts,releases,audit}` | Authoring and inspection |
| `POST /v1/admin/scopes/{id}/{drafts,validate,rollout,rollback}` | Draft creation, validation and deployment operations |
| `GET/PUT /v1/admin/drafts/{id}` | Versioned draft read/write |
| `POST /v1/admin/drafts/{id}/{submit,approve,publish}` | Frozen review and signed publication |
| `GET /v1/runtime/scopes/{id}/active.jws` | Stable anonymous release pointer |
| `GET /v1/runtime/scopes/{id}/active/{0..99}.jws` | Finite anonymous cohort pointers |
| `GET /v1/runtime/releases/{id}.jws` | Immutable signed release |
| `GET /v1/runtime/resources/{sha256}.json` | Immutable digest-addressed resource |

Admin responses are `no-store`; public pointers cache for 15 seconds, immutable artifacts for a year. Separate admin and public Host authorities are enforced. Public GETs allow credential-free CORS; admin cross-origin requests are rejected. No account token, private signer or arbitrary client-supplied tenant entitlement participates in public resolution.

## Non-demo process

`npm start` requires:

| Variable | Value |
| --- | --- |
| `OPENMUSE_CONFIG_DATABASE` | SQLite file path on durable storage |
| `OPENMUSE_CONFIG_SIGNING_KEY_FILE` | Ed25519 PKCS#8 private-key PEM, mode 0600 |
| `OPENMUSE_CONFIG_SIGNING_KEY_ID` | Public key ID pinned in client bundles |
| `OPENMUSE_CONFIG_PUBLIC_ORIGIN` | Configured HTTPS distribution origin, no path/query |
| `OPENMUSE_CONFIG_ADMIN_ORIGIN` | External admin origin for Host/Origin checks |
| `OPENMUSE_CONFIG_PRINCIPALS_FILE` | Owner-readable JSON secret file, mode 0600 |
| `OPENMUSE_CONFIG_MESSAGE_REGISTRY_FILE` | Optional product catalog JSON; defaults to the native client registry |
| `OPENMUSE_CONFIG_PLUGIN_REGISTRY_FILES` | Optional JSON array of absolute paths to trusted plugin catalogs, merged with the product catalog (maximum 32) |
| `OPENMUSE_CONFIG_BIND` | Optional listen address; defaults to loopback |
| `OPENMUSE_CONFIG_LISTEN_PORT` | Optional internal port; otherwise origin port or 8790 |

Principal file shape:

```json
[
  {"id":"configuration-editor", "token":"replace-with-a-separate-random-secret-of-at-least-32-characters", "roles":["reader","editor"], "scopes":["deployment-scope"]}
]
```

Available roles: `reader`, `editor`, `approver`, `publisher`, `admin`. Give independent principals separate secrets and explicit scope lists; `*` must be explicit. Production ignores development identity headers. Tokens stay in the admin page's memory and are never stored in a URL or browser persistence. Place the listener behind an authenticated HTTPS ingress and isolate `/v1/admin/` from the public distribution ingress. This bearer adapter is an integration boundary for the eventual organization identity provider.

Private signing keys are outside the database and public APIs. Before rotating the active signer, ship overlapping public roots in installed client bundles. A normal dynamic release cannot change its own root of trust. The reference process uses one local signer; KMS/HSM delegation and threshold approvals are deployment work, not implemented here.

## Verify

```sh
npm test
```

Tests cover real HTTP authorization/Host/Origin handling, independent review, optimistic concurrency, durable restart, JWS signatures, resource digests, deterministic cohorts, reviewed rollback and scope isolation. `test/runtime-fixture.mjs` supplies public signed artifacts for the Dart integration test. `test/check-html-runtime.mjs` verifies message AST parity and host-owned HTML language updates against a DOM.

No production keys, CDN, ingress, user credentials or production releases are created by these tests.


## Public installation bundle preparation

Run these commands in a trusted provisioning workspace, using your chosen paths, scope and HTTPS distribution origin:

```sh
npm run keygen -- --directory /private/config-signing --kid config-root-v1
npm run prepare-bundle -- --input /path/to/deployment.json --output /path/to/installed-deployment.json --scope deployment-scope --origin https://config.example.test --public-keys /private/config-signing/config-root-v1.public.json
```

Both tools refuse to overwrite existing output. Only the public JSON belongs in an installation bundle; the private PEM remains in the signer environment. The prepared bundle trusts that signer and resource origin, selects the scope feed, and enables anonymous cohort routing for compatible clients. Compile it with the SDK deployment compiler or publish it as the website's installed deployment data. Website SSR currently consumes the stable feed and does not select visitor cohorts.

To author website packs, set `OPENMUSE_CONFIG_MESSAGE_REGISTRY_FILE` to the absolute path of Muse-WebSite's generated `config/messages.catalog.json` before starting this process. The admin messages remain available. This reference process binds one product message contract; simultaneous contract versions require a versioned registry service rather than changing the registry under existing scopes.

Plugin catalogs own a `plugin.*` namespace and declare `sourceRevision`, `contractHash`, and `interpolation.v1` message definitions. The admin editor preserves these contract fields when composing packs. Add `plugin-messages.v1` to a release's required capabilities when attaching plugin packs. Published resources use `kind: pluginMessages` and `delivery: onDemand`, including for the default language; they never enter the Host's ICU catalog. The Host verifies the signed reference and content digest before delivering public presentation data through MCP Apps Host Context. Each plugin validates its own message contract. For GenOffice PPTX, register `Muse-Plugin-Ecosystem/plugins/genoffice-pptx/i18n/catalog.json`; its configuration and translation workflow are documented in that plugin's `GLOBALIZATION.zh-CN.md`.


## Runtime switches and downloadable languages

Native snapshots can carry `settings.features` and `settings.parameters` with the `settings.v1` capability. The admin editor exposes plugin-market availability, update prompts and a bounded configuration refresh interval. Values pass the same independent approval, immutable publication and rollback flow as other snapshot fields. They do not grant account permissions.

`messages.dynamic.v1` snapshots may register additional locales through `localization.localeCatalog`. Keep installed fallback languages enabled and attach non-empty registered-message packs for every new language. The publisher marks non-default, non-bundled language resources `onDemand`; only eager resources enter `bundleRefs`. The native SDK downloads these lazily from the authenticated manifest and persists them with the signed cache record. Add one language and its packs together in a draft; client rendering capabilities remain authoritative.
