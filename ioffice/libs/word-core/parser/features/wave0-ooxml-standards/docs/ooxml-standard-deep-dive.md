# OOXML 国际标准详解：历史、理念与「文档长什么样」

**标准全称**: Office Open XML（常简称 **OOXML**）  
**正式标准号**: **ISO/IEC 29500**（源自 **ECMA-376**）  
**本目录语境**: 读 DOCX / WordprocessingML 解析代码前的概念底座  
日常所说的 **DOCX** = 符合 **OPC** 的 ZIP 包 + 以 **WordprocessingML** 为主的一组 Parts。

---

## 0. 一句话结论（先回答你的核心疑问）


| 问题                           | 结论                                                                           |
| ---------------------------- | ---------------------------------------------------------------------------- |
| OOXML 有没有规定文档的**物理排版与渲染结构**？ | **没有**完整规定。它不定义「第 N 页第 M 行像素级落点」的固定版面树。                                      |
| 那它规定什么？                      | 规定 **逻辑文档模型**（段落 / Run / 表格 / 样式…）+ **一组可解释的格式化意图**（字体、缩进、页边距、浮动定位…）。        |
| 文档「长」成什么样由谁决定？               | 由 **实现者的排版引擎**根据这些意图计算出来。同一份 DOCX，Word / WPS / LibreOffice 可以「语义等价、像素不完全一致」。 |
| 和 PDF 的本质差别？                 | PDF ≈ **最终呈现（fixed layout）**；DOCX/OOXML ≈ **可编辑的逻辑稿 + 格式意图（reflowable）**。    |


更精确的说法：

> OOXML **不是**「屏幕/纸张上的画布描述语言」，而是「**带样式的可编辑文档对象模型**」。  
> 它告诉实现：**内容是什么、作者希望怎样排**；**不**把每一次换行、分页、字形 hint 固化成唯一真相。

## 1. 历史背景：它为什么会出现



### 1.1 前史：封闭的二进制 Office 格式

1990s–2000s，Microsoft Office 的默认格式是 **OLE 复合文档 + 私有二进制结构**（`.doc` / `.xls` / `.ppt`）。特点：

- **高效、功能完整**，与 Word 内部内存模型高度耦合（PLC、CHPX、PAPX 等概念就源自这条血统）
- **规格不开放或极难完整实现**：第三方互操作成本高，政府/企业担心「格式锁定」
- 文档即「某一版 Word 引擎的序列化状态」，而不是「中立的、可长期归档的文档语言」

同一时期，开放文档格式运动升温：**OpenDocument Format（ODF，ISO/IEC 26300）** 成为「开放办公文档」的旗帜之一。

### 1.2 动机：开放、XML、ZIP、互操作压力

微软推动 OOXML 的现实动机可概括为：

1. **客户与监管压力**：公共采购要求开放标准；「格式必须可被多方实现」
2. **XML 化**：用 XML 表达文档结构，便于工具链处理、差分、校验、长期可读
3. **包化（ZIP）**：把主文档、样式、图片、页眉页脚拆成 **Parts**，而不是一个巨大二进制 blob
4. **兼容既有生态**：必须能承载 Word 几十年的功能面（修订、域、复杂编号、浮动对象、兼容选项…），不能为了「干净」而砍掉现实需求



### 1.3 标准化路径（时间线精简）


| 阶段         | 事件                                                         | 意义                                             |
| ---------- | ---------------------------------------------------------- | ---------------------------------------------- |
| ~2005–2006 | Microsoft 将 Office XML 格式提交 **ECMA**                       | 从「产品格式」走向「可公开引用的规范」                            |
| 2006       | **ECMA-376** 第 1 版发布                                       | OOXML 的工业标准起点                                  |
| 2008       | **ISO/IEC 29500** 批准                                       | 成为国际标准；同时留下巨大争议（与 ODF「双标准」并存）                  |
| 之后         | ECMA-376 / ISO 29500 多版修订；**Transitional** 与 **Strict** 分流 | 现实世界大量 DOCX 仍是 **Transitional**（贴近 MS Word 产物） |


争议焦点（理解标准气质很重要）：

- OOXML **极大、极细、偏兼容历史 Word 行为**
- 批评者认为它「标准化了一个产品的实现细节」；支持者认为「只有这样才覆盖真实文档宇宙」
- 对本项目：我们面对的是 **真实 Word 产物**，路径偏 **Transitional**，而不是理想化的 Strict 子集



### 1.4 它在标准族中的位置

```text
ISO/IEC 29500 (OOXML)
├── Part 1  Fundamentals / Markup Language Reference
│     ├── WordprocessingML   ← DOCX 正文语义（本目录重点）
│     ├── SpreadsheetML
│     ├── PresentationML
│     └── DrawingML 等共享标记
├── Part 2  Open Packaging Conventions (OPC)  ← ZIP + Relationships
├── Part 3  Markup Compatibility and Extensibility (MCE)
└── Part 4  Transitional Migration Features（过渡/兼容特征）
```

日常「打开一个 `.docx`」= **OPC 包** + **WordprocessingML 主文档** + styles / numbering / settings / headers… 等卫星 Parts。

## 2. 核心理念：OOXML 到底在「承诺」什么



### 2.1 三条立柱

1. **开放包（OPC）**
  文档是 **ZIP 里的一棵部件图**，部件用 **Relationship** 连接，而不是硬编码路径拼装。  
   → 见 [opc-package.md](./opc-package.md)
2. **标记语言描述文档对象**
  Word 文档用 **WordprocessingML** 描述：段落、Run、表格、节、域、修订…  
   → 见 [wordprocessingml.md](./wordprocessingml.md)
3. **兼容与扩展共存（MCE）**
  允许「主标准 + 厂商扩展」共存于同一 XML，消费者可忽略不懂的扩展。  
   → 现实 DOCX 里常见 `mc:Ignorable`、`w14:` / `w15:` 等命名空间



### 2.2 设计哲学（相对 PDF / HTML）


| 维度        | OOXML (DOCX)       | PDF            | HTML+CSS          |
| --------- | ------------------ | -------------- | ----------------- |
| 主目标       | **可编辑办公文档** 的交换与存档 | **固定呈现**、打印保真  | **结构+表现分离**的超文本文档 |
| 内容模型      | 段落/表格/节/样式为中心      | 页面上的绘图指令与文本对象  | DOM 树 + 盒模型       |
| 换行/分页     | **运行时计算**          | 往往已固化          | 运行时计算             |
| 「长什么样」的权威 | **弱权威**（意图 + 引擎）   | **强权威**（页面即真相） | 弱权威 + CSS 约束      |
| 编辑友好      | 极高                 | 低              | 中高                |


OOXML 的核心承诺可以写成：

> **语义可交换、格式意图可交换、呈现尽量一致；但不保证跨引擎像素级一致。**



### 2.3 「意图」而不是「画布」

WordprocessingML 里大量属性是 **作者意图（authorial intent）**：

- 「这段居中」「首行缩进 2 字符」「用 Heading 1 样式」
- 「这一节 A4、上下边距 2.54cm」
- 「这张图环绕文字、距左 3cm」

实现者必须：

1. **解释**这些意图（属性合并、样式层叠、主题色、兼容模式…）
2. **排版**出具体行盒、页盒、浮动锚点
3. **渲染**字形、边框、底纹、图片

标准定义的是步骤 1 的 **词汇与语义边界**；步骤 2–3 属于 **实现算法空间**（可有参考行为，但不是像 PDF 那样把结果本身存下来）。

## 3. 它定义了什么



### 3.1 包层（OPC）——「文件怎么装」

- Package = ZIP
- Part = 包内资源（XML / 图片 / 嵌入对象…）
- `[Content_Types].xml` = MIME 类型表
- `_rels` = 部件关系图（主文档指向谁、图片挂在哪）

这解决的是 **物理文件组织**，不是排版。

### 3.2 文档层（WordprocessingML）——「内容与格式意图怎么写」

核心对象（简化）：

```text
Package
  └── document.xml
        └── body
              ├── p (段落)
              │     ├── pPr (段落属性 / 样式引用)
              │     └── r (Run)
              │           ├── rPr (字符属性)
              │           └── t  (文本) | br | tab | drawing | …
              ├── tbl (表格)
              └── sectPr (节属性：页面/页眉页脚/分栏…)
  └── styles.xml / numbering.xml / settings.xml / headers / media …
```

还定义了大量「办公文档现实」：

- 样式与样式继承（见 [styles-numbering-settings.md](./styles-numbering-settings.md)）
- 多级编号
- 节与页眉页脚（见 [section-breaks.md](./section-breaks.md)）
- 域（Field）、目录、交叉引用
- 修订、批注、脚注尾注
- 表格合并、嵌套
- 浮动图形（DrawingML / 旧 VML）的锚定与环绕



### 3.3 它**不**定义什么（同等重要）

- **不**定义完整的 **分页算法**（widow/orphan、浮动避让、脚注布局的唯一算法）
- **不**定义 **字形选择与 hinting** 的唯一结果（字体缺失、度量差异会导致重排）
- **不**定义 **屏幕像素级** 的唯一渲染树
- **不**把「第 3 页第 12 行」作为一等公民存进格式（那是引擎算出来的）

## 4. 它解决了什么问题


| 痛点              | OOXML 的解法                             |
| --------------- | ------------------------------------- |
| 二进制私有、难互操作      | XML + 公开规范 + ZIP Parts                |
| 单文件巨石、难局部替换     | Part + Relationship：换一张图不必重写全文        |
| 功能面巨大（修订/域/编号…） | 极细的标记词汇表，尽量覆盖 Word 能力                 |
| 需要长期可读/工具处理     | 文本化 XML（仍可配合二进制嵌入）                    |
| 多厂商扩展           | MCE：可忽略扩展，主语义仍可消费                     |
| 与旧 .doc 生态共存    | Transitional 特征、兼容设置、大量「像 Word 一样」的选项 |


对本仓库（word-core）而言，OOXML 解决的是：

> **如何把「外部可交换的 DOCX」可靠地映射进内核的逻辑存储**（文本绳、CHPX/PAPX、PLCSection…），而不是如何在标准里找到一份「现成的页面树」。

映射关系见 [mapping-to-kernel.md](./mapping-to-kernel.md)。

## 5. 文档应该如何「表示」：三层模型

理解 OOXML，建议始终分层，不要混为一谈：

```text
┌─────────────────────────────────────────────────────────┐
│ L3  呈现（Presentation）                                 │
│     屏幕像素 / 打印墨点 / 无障碍朗读流 …                  │
│     ← 标准几乎不规定；由渲染器完成                        │
├─────────────────────────────────────────────────────────┤
│ L2  排版结果（Layout Result）                             │
│     行盒、页盒、浮动位置、分页点、表格行高 …               │
│     ← 标准不持久化为「唯一真相」；由排版引擎计算            │
├─────────────────────────────────────────────────────────┤
│ L1  逻辑文档 + 格式意图（Document Model）  ★ OOXML 主场   │
│     段落/Run/表格/样式/节属性/定位意图 …                  │
│     ← ISO/IEC 29500 WordprocessingML 主要定义这里         │
├─────────────────────────────────────────────────────────┤
│ L0  包（Package）                                        │
│     ZIP + Content Types + Relationships                  │
│     ← OPC                                               │
└─────────────────────────────────────────────────────────┘
```

**DOCX 文件主要序列化的是 L0 + L1。**  
L2/L3 在打开文档时由应用重建；关闭时通常**丢弃**（除非另存为 PDF 等固定版式）。

## 6. 「排版」在标准里到底出现到什么程度

这是最容易误解的一点：**OOXML 有排版相关属性，但没有完整排版系统规范。**

### 6.1 它确实描述了「页面级约束」（偏物理参数）

通过 `w:sectPr` 等，文档可以声明例如：

- 纸张大小、方向（`pgSz`）
- 页边距（`pgMar`）
- 分栏
- 页眉页脚距离
- 文档网格（中文排版常见）
- 节类型（下一页分节 / 连续分节…）

这些是 **页面坐标系上的约束与偏好**，接近「物理页面设置」，但仍然不是「已排好的每一页」。

### 6.2 它描述了「流式排版意图」（逻辑 + 度量）

段落 / 字符属性例如：

- 对齐、缩进、段前段后、行距
- 字体、字号、加粗、颜色、高亮
- 分页控制（段前分页、保持同页…）——**意图**，非结果
- 制表位
- 编号与列表缩进

表格属性例如：列宽偏好、自动适应、单元格边距、合并。

这些决定 **算法输入**，不决定 **算法输出快照**。

### 6.3 它描述了「定位对象」的锚点模型（局部物理）

浮动图、文本框等可以带：

- 锚定到段落/页
- 环绕方式
- 相对页边距/栏/段落的偏移

这是 **局部几何意图**。最终是否溢出、如何避让、是否推迟到下页，仍由引擎决定。

### 6.4 它没有给出的东西（对照你的疑问）


| 你可能期望的「物理排版结构」              | OOXML 是否提供  |
| --------------------------- | ----------- |
| 完整的页面树（Page → Line → Glyph） | **否**（一般不存） |
| 每个字符的基线坐标                   | **否**       |
| 强制唯一的换行点列表                  | **否**       |
| 打印预览的权威位图                   | **否**       |
| 与某版 Word「像素一致」的合规测试集        | **无此保证**    |


所以：

> OOXML **规定文档应如何被理解与编辑**；  
> **不**规定文档在某一设备上必须排出的唯一物理结构。

## 7. 文档应该「长」成什么样：标准如何「指定外观」



### 7.1 外观 = 内容树 × 样式层叠 × 主题 × 兼容模式 × 引擎

「长什么样」在 OOXML 世界里是一条推导链：

```text
直接格式 (rPr / pPr)
    ⊕ 段落样式 / 字符样式 / 表格样式 / 编号样式
    ⊕ docDefaults
    ⊕ theme（主题字体/颜色）
    ⊕ settings（兼容选项、镜像边距…）
    ⊕ 实现默认值与字体度量
    ──排版引擎──►  行/页/浮动几何
    ──渲染器──►    最终像素或打印结果
```

标准负责定义 **左边大部分输入词汇的含义**；  
**右边的几何与像素**属于产品实现。

### 7.2 「长得像 Word」来自哪里

人们觉得「DOCX 有确定外观」，通常是因为：

1. **Microsoft Word** 是事实参考实现（de facto）
2. 大量属性与兼容开关就是为了对齐 Word 历史行为
3. 测试时用 Word 打开对比

但从 **标准合规** 角度：

- 实现 A 与实现 B **允许**在换行、分页、浮动上有差异
- 「严格同屏」不是 ISO 29500 的交付物；那是 **PDF/XPS** 或「导出固定版式」的目标



### 7.3 和本内核的关系（务实视角）

解析 DOCX 时，importer 的任务是把 L1 **忠实地搬进内核模型**：


| OOXML           | 内核（概念）           |
| --------------- | ---------------- |
| `w:t` 文本        | 文本绳中的字符          |
| `w:r` + `w:rPr` | CHPX 区间          |
| `w:p` + `w:pPr` | PAPX             |
| `w:sectPr`      | PLCSection / 节属性 |
| styleId / numId | 样式表与编号模型         |


**排版与渲染**发生在内核之后的 layout / render 管线；  
**不要**指望在 `document.xml` 里读到「已经排好的页面结构」。

## 8. 用三个对照把概念钉死



### 8.1 OOXML vs PDF


|       | OOXML       | PDF        |
| ----- | ----------- | ---------- |
| 存的是什么 | 可编辑逻辑稿 + 意图 | 大致「怎么画出来」  |
| 换纸张尺寸 | 通常整体重排      | 往往需要重新生成   |
| 适合    | 协作编辑、二次排版   | 归档、印刷、保真分发 |




### 8.2 OOXML vs ODF

两者都是 **可编辑办公文档的开放 XML 格式**，都偏逻辑模型。差异更多在：

- 词汇表与包结构不同
- 功能覆盖与「贴近哪家办公套件」的历史路径不同
- 本项目 DOCX 路径走 OOXML，不在此展开 ODF



### 8.3 OOXML vs「排版语言」（TeX / CSS 分页）

TeX / 部分 CSS 规范会更明确地讨论盒子、断行、浮动规则。  
OOXML 的重点是 **办公文档功能完备的序列化**，排版规则散落在属性语义与实现惯例中，**不是**一部独立的「排版算法标准书」。

## 9. 常见误解


| 误解                     | 校正                           |
| ---------------------- | ---------------------------- |
| 「DOCX 里已经有完整页面结构」      | 通常没有；打开时才分页                  |
| 「符合 OOXML = 各软件显示一模一样」 | 只保证语义层可交换；呈现可有差异             |
| 「sectPr 就是排版引擎」        | sectPr 只是节/页面设置；不是 layout 结果 |
| 「解析完 XML 就等于渲染完成」      | 解析只恢复 L1；还要样式解析、排版、绘制        |
| 「OPC 决定版式」             | OPC 只决定怎么打包 Parts            |

## 附录 A：若只能记住五句话

1. **OOXML = OPC 包 + ML 标记**；DOCX 是其 Word 形态。
2. 它主要定义 **逻辑结构与格式意图**，不是最终版面快照。
3. **页面设置与定位属性**存在，但 **分页/换行结果**由引擎计算。
4. 「长什么样」= 意图 × 样式层叠 × 字体度量 × 排版实现。
5. 解析器的职责是重建 **可编辑文档模型**；排版器的职责才是让它「长」出来。
