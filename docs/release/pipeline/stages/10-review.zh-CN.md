# 10-review · 审核跟进与拒审修复

负责人：发布、研发及产品负责人。状态与证据单独保存在每次发布的 `stages/10-review.json`。

## 输入与目标

区分待审核、审核中、被拒、通过；收到反馈后生成可追踪的修复闭环。

前置节点：09-submit。

## 执行步骤

- 读取控制台和开发者通知中的实际状态，记录日期、平台原文、问题代码、对应功能和负责人。
- 拒审拆成独立缺陷/需求；修改代码重走开发、隐私、测试、构建、最终包和材料的受影响节点。
- 使用新构建号，关联被拒构建与修复构建；不删除失败日志，不用新截图覆盖旧版本证据。
- 审核期间保持演示账号与 Desktop 可用，监测登录、文档资源和邮件。
- 申诉/回复需要准确说明可复现步骤和修复；使用已授权的控制台沟通流程。
- 收到明确平台通过回执才将此节点设为 passed。当前案例没有获批/公开上架证据。

## 输出与验收

审核事件记录、反馈原文、缺陷及修复映射、通过回执；尚待结果时为 pending/in_progress。

证据不足保持 partial/pending；通过后由负责人填写 passed、owner 和 evidence。后续修改使本节点结论失效时，重新打开相关节点。
